# Introduction {#ch-intro}

## What VANTA is

**VANTA** stands for *Virtualized Adversarial Network & Technical Assessment*. Its motto is:

> "Don't give the contestant a problem. Give them a world."

VANTA is a platform for technical challenges and hackathons in the C language. Instead of
handing someone a fixed exercise ("write a function that reverses a list"), VANTA builds a small,
working-but-broken *system* on demand. One example is a scheduler for a shared 3D printer. Another
is a booking system for parking spots. The system has a real defect hidden in it. The contestant's
job is to work out what is wrong, test their theory, and submit C code that fixes it.

Three things make VANTA different from an ordinary problem set:

1. **Nothing is stored in advance.** There is no bank of problems and no answer key. Every world
   is generated by a program from a random number (a *seed*). The person who wrote VANTA doesn't
   know in advance what a given seed will produce.
2. **Every world is proven before anyone sees it.** VANTA compiles and runs each candidate world
   and checks three things. The planted bug really makes the hidden tests fail. The world can be
   fixed. And at least two *architecturally different* fixes pass. Worlds that fail any check
   are thrown away.
3. **Investigation without arguing with bots.** Earlier versions of the project used chat-bot
   characters with written backstories. Contestants ended up trying to talk the bots into
   revealing the answer. VANTA replaces this with *execution-grounded witnesses*. These are people
   whose every statement is computed by actually running the broken system. A *probe lab* lets
   contestants design their own experiments.

## The problems VANTA was built to solve

| Problem with typical challenge platforms | How VANTA answers it |
|---|---|
| Problems leak. Solutions get shared online and copied. | Every world is generated fresh. In a cohort, each person's world has different names and numbers, so copied code doesn't even compile. |
| One "correct" answer encourages pattern-matching. | Each world is proven to admit at least two different correct designs. |
| Chat-bot "characters" get argued with in circles. | Witnesses hold no facts. Their answers come from running code, so the same question always gets the same answer and there is nothing to argue about. |
| Beginners and experts get the same difficulty. | Each person has a rating. The next world is evolved to sit slightly above their level. |
| A grader that is a person or a language model can be inconsistent. | Grading is pure execution: compile, run hidden tests under sanitizers, read the results. |

## Design principles

These ideas show up again and again in the code. Knowing them makes every file easier to read.

- **Programs, not content.** An *archetype* is a Python class that *writes* a world (C code,
  tests, story) from a seed. It fixes only the *shape* of a defect, never its concrete numbers or
  names.
- **Prove it by running it.** Whenever VANTA claims something about a world, a compiler and a
  test harness back the claim up. Examples are "it's broken", "it's fixable", "this witness
  waited 5 days" and "these two numbers disagree".
- **Many correct answers.** The fitness function rewards worlds where several different fixes
  pass. Witness replays expose the *trade-offs* between correct designs.
- **Bounded interaction.** Every question gets one answer. No component ever gets into an open-ended
  conversation that a contestant could "win".
- **Deterministic.** The same seed (and the same settings) always produces the same world. That
  makes bugs reproducible and results fair.
- **One store, many views.** The web UI and the Discord bot are both clients of the same HTTP API
  and the same database.

## What is in the box

| Area | Feature | Where it lives |
|---|---|---|
| Generation | Two defect classes (*archetypes*), each with three bug variants and several story settings | `backend/app/worldgen/` |
| Generation | Evolutionary search: generate → compile → test → score → select → mutate | `backend/app/evolution/` |
| Grading | C sandbox with a static safety check, sanitizers and timeouts; hidden-test harness protocol | `backend/app/execution/`, `backend/app/worldgen/evaluate.py` |
| Investigation | Probe lab: contestant-written experiments run against the original system or their own code | `backend/app/investigation/probes.py` |
| Investigation | Witnesses who lived through one real run, can be asked bounded questions, and can relive the same period under the contestant's code | `backend/app/investigation/witnesses.py` |
| Adaptation | Chess-style (Elo) rating per person and calibrated difficulty for the next world | `backend/app/core/profiles.py` |
| Groups | Cohorts: one defect for a whole room, a unique world per member, a host console | `backend/app/core/cohorts.py` |
| Groups | Originality analysis: how many genuinely different approaches were accepted | `backend/app/core/originality.py` |
| Interfaces | Web workbench (React + TypeScript) | `frontend/` |
| Interfaces | Discord bot with 16 slash commands | `discord_bot/` |
| Quality | 35 automated tests covering generation, investigation, cohorts and Discord | `backend/tests/` |
